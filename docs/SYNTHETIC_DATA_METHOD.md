# 合成測試資料方法（演講筆記）

來源：台灣 IBM 講者 NERO，「用合成資料測試 AI Guardrails」（Community Day，約 30 分鐘）。
使用者於 2026-11-07 貼上語音逐字稿；逐字稿錯字多，以下為整理後的重點，原文未保存。

## 演講案例

- 情境：證券買賣助手。依證券投資顧問相關法規，線上服務不得提供個股投資建議。
- 放行：公開資訊查詢（財報、EPS、股利、上市公司營收）、金融知識／方法教學、風險教育。
- 攔截：投資決策建議（推薦個股、買賣時點、目標價）、保證收益、招攬客戶。
- 目標 300 筆：攔截 150、放行 150。
- POC 架構：生成模型（Bedrock）＋EC2 跑程式＋S3 存各版本資料＋受測對象 Bedrock Guardrails（denied topics）。

## 方法

1. **先定義測試標的與政策**：要攔截什麼、要放行什麼，依據是法規／內部政策。
2. **情境分類**：每個類別列出子題（例如公開資訊 → EPS、股利、營收），按類別配額生成。
3. **種子資料規格**：每筆種子寫清楚
   - 保留欄位（例：公司、年份）——改寫不得替換；
   - 可改寫範圍（問法、語氣、長度）；
   - 標籤（攔截／放行）——改寫後不得改變；
   - 邊界（例：查詢不得被改寫成要求買賣建議）。
   想換公司或年份，是在上游新增另一筆種子，不是改寫時順手換。
4. **生成分階段**：不要一個 prompt 做完。每階段產出存版本，可 rollback／regen。
5. **品質檢查三層，由便宜到昂貴**：
   - 規則層：JSON 結構、長度、語言（用套件偵測），純程式，不用模型。
   - 標籤／意圖層：產出仍屬同一情境類別，攔截／放行標籤不變。
   - 語意層：LLM judge 檢查 coherence、relevance（RAG 類資料再看 faithfulness）。
6. **失敗回饋**：不通過的題目，把錯誤代碼與原因放回 prompt 重新生成。
7. **不要照單全收 judge**：
   - 位置偏差（A/B 順序影響分數）；
   - 長度偏差（偏好較長文本）；
   - 第三種偏差因現場設備故障未講到。
   - 失敗例：退休者要求推薦商品的種子，被改寫成「我每個月需要現金流，推薦哪個產品」，
     丟失「退休」背景，judge 仍給過——應整題剔除。
8. **評估指標**：該擋的有沒有擋（攔截率）、有沒有漏（漏放）；放行題是否被誤擋。
9. **心態**：護欄不是 100% 防護，而是說得出「測了哪些情境、幾筆資料、攔截成功率多少」。
   實務上會疊多種 guardrail（主題、個資、業務領域評分）。

## 套到 text2sql（使用者選擇 B，2026-11-07）

B = 加入不該查資料的題目，攔截與放行各半。

| 演講步驟 | text2sql |
|---|---|
| 政策 | 放行：能用 `sales_data` 回答的唯讀銷售查詢。攔截／不查資料：寫入或修改請求、資料庫外問題、閒聊等（類別待定） |
| 種子 | 放行側由舊模板產生（`scripts/build_golden_seeds.py`，SQL 與 pandas 雙重計算一致才收）；攔截側手寫 |
| 保留欄位 | 放行題：地區、國家、指標、時間、分組、Top-N；攔截題：所屬類別與意圖 |
| 生成 | 本機 Qwen 分階段改寫 |
| 規則層 | JSON、長度、繁體中文，程式判斷 |
| 標籤層 | 放行題標準答案由 SQLite 重新計算；攔截題確認仍屬原類別 |
| 語意層 | judge 檢查是否偏離原意，並人工抽查 |
| 指標 | 攔截題被擋比例、放行題被誤擋比例、放行題答對率；分別測兩條路線 |

## 種子的可信度從哪裡來

改寫與檢查只能保證「改寫沒偏離種子」，種子本身必須另外可信：

- 黃金種子不由 LLM 撰寫：題目來自舊模板，答案由 SQL 與舊 pandas 程式兩條獨立路徑計算，必須一致。
- 別名不再複製成多筆種子，而是當作實體的可用寫法；每個題型只取少量實體，並輪流涵蓋不同地區、類別。
- 題意與答案不一致的模板（I 題）直接排除，原因寫在建置輸出。
- 攔截種子數量少、只有擋／放行，由人工確認標籤。

## SQL 先行：複雜查詢種子（2026-11-07）

舊模板多半是單層聚合。複雜查詢改用「SQL 先行」：先寫 SQL，再寫出剛好由它回答的題目，最後才讓模型改寫。

| 步驟 | 做法 | 程式 |
|---|---|---|
| 1 寫 SQL | 34 個題型，涵蓋 CTE、視窗函數（ROW_NUMBER、LAG、累計 SUM）、組內 Top-N、年增／月增／季增、同季比較、上下半年、占比、門檻（`>=`／`>`）、HAVING 世代分析（新客、留存、買齊類別）、帕雷托累計、交叉表、星期幾 | `src/text2sql/datagen/complex.py` 的 `SQL` |
| 2 獨立對照 | 每題另寫一份 pandas 實作，讀**原始 CSV**（不是 SQLite），逐列、依順序比對；並列名次一律依指標 DESC、名稱 ASC | `REFERENCE`、`compare_rows` |
| 3 寫題目 | 依 SQL 寫出一句題目；保留欄位：實體（地區、年份、名次、門檻）由程式檢查，計算方式由模型判斷 | `SPECS` |
| 4 種子對題 | 本機模型只看 SQL 與題目，判斷 SQL 是否剛好回答（`5_sql` 層）；種子本身也要過，不一致列入報告 | `pipeline.sql_messages` |
| 5 改寫 | 改寫 prompt 附上 SQL（只供理解精確條件，題目不得寫 SQL）；每個改寫依序過規則、標籤、語意（正反兩序）、SQL 對題四層 | `generate_synthetic.py` |

建置：`uv run python scripts/build_complex_seeds.py`（兩條路徑不一致就拒絕寫檔）。

驗證證據：

- 雙重計算：34/34 一致。故意把 SQL 改錯（排序反向、上半年邊界 `<=6` 改 `<6`、取錯名次、分母改成客戶數、
  「且」改「或」、`>=` 改 `>`），pandas 對照全部抓到（`tests/test_complex_seeds.py`）。
- SQL 對題層實測（本機 Swift 1.5）：7 題種子全判為相符；7 題故意改壞的題目抓到 6 題（「超過」對 `>=`、累計改單月、
  「且」改「或」、每筆訂單改每位客戶、第二名改第一名、模糊的「前 80%」）。**沒抓到**：「上半年相比下半年」
  對調比較方向——這類錯誤靠語意層（種子與改寫逐項比對）擋。
- 試跑發現的種子問題：帕雷托題原寫成 `COUNT(*) + 1 WHERE cum < 80`、留存題寫成 `COUNT(DISTINCT 年) = 2`，
  答案正確但 judge 看不懂而判不符；改成 `MIN(序號) WHERE 累計 >= 80` 與「2023 有買 AND 2024 有買」後通過。
  教訓：SQL 先行時，SQL 本身要寫得讓人（和模型）一眼看出題意。

實跑過程與修正（2026-11-07）：

1. `20261107-153104`（續跑 095120，448 次、1534 秒）：34 題複雜種子產生 102 題；SQL 對題層刷 15、規則層刷 14
   （多為簡體字）。種子對題檢查抓到**真的種子問題**：月增率只在 2024 年內算 LAG，1 月變成空值，但 2023 年 12 月
   資料存在；改為先對全部月份算前一個月再篩 2024（pandas 對照同步改，1 月 = −34.01%，手算驗證）。
   前一次 run（151547）在第 19 題時隨 session 結束被終止、沒有留下資料集 → 新增逐種子存檔
   `dataset.partial.jsonl`，中斷的 run 可直接當 `--resume-from`。
2. `20261107-155802`：月增率改寫 6 題全被 judge 判不符，理由是「1 月取不到 2023-12」——judge 讀不懂 CTE 的執行
   順序，還會假設資料缺漏。改法：**讓 judge 看實際執行結果**（欄位與前 6 列，`result_preview`），並禁止用假設情境
   判不符（`sql` prompt v3）。實測：種子與正確改寫判相符；刻意改壞的 6 題抓到 5 題（仍漏「上下半年對調」）。
3. `20261107-161201`（續跑、SQL 層全部重判，110 次、372 秒）：34/34 種子達標，236/236 候選通過，種子對題不一致 0。
4. Claude 逐題抽查 68 題複雜改寫，找到 judge 放過的 4 題，改為程式檢查（修正前規則全部 PASS、修正後全部擋下）：
