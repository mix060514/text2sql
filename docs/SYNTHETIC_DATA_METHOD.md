# 合成測試資料方法（演講筆記）

來源：台灣 IBM 講者 NERO，「用合成資料測試 AI Guardrails」（Community Day，約 30 分鐘）。
使用者於 2026-11-07 貼上語音逐字稿；逐字稿錯字多，以下為整理後的重點，原文未保存。

## 演講案例

- 情境：證券買賣助手。依證券投資顧問相關法規，線上服務不得提供個股投資建議。
- 放行：公開資訊查詢（財報、EPS、股利、上市公司營收）、金融知識／方法教學、風險教育。
- 攔截：投資決策建議（推薦個股、買賣時點、目標價）、保證收益、招攬客戶。
- 目標 300 筆：攔截 150、放行 150。
- POC 架構：生成模型（Bedrock）＋EC2 跑程式＋S3 存各版本資料＋受測對象 Bedrock Guardrails（denied topics）。

## 方法

1. **先定義測試標的與政策**：要攔截什麼、要放行什麼，依據是法規／內部政策。
2. **情境分類**：每個類別列出子題（例如公開資訊 → EPS、股利、營收），按類別配額生成。
3. **種子資料規格**：每筆種子寫清楚
   - 保留欄位（例：公司、年份）——改寫不得替換；
   - 可改寫範圍（問法、語氣、長度）；
   - 標籤（攔截／放行）——改寫後不得改變；
   - 邊界（例：查詢不得被改寫成要求買賣建議）。
   想換公司或年份，是在上游新增另一筆種子，不是改寫時順手換。
4. **生成分階段**：不要一個 prompt 做完。每階段產出存版本，可 rollback／regen。
5. **品質檢查三層，由便宜到昂貴**：
   - 規則層：JSON 結構、長度、語言（用套件偵測），純程式，不用模型。
   - 標籤／意圖層：產出仍屬同一情境類別，攔截／放行標籤不變。
   - 語意層：LLM judge 檢查 coherence、relevance（RAG 類資料再看 faithfulness）。
6. **失敗回饋**：不通過的題目，把錯誤代碼與原因放回 prompt 重新生成。
7. **不要照單全收 judge**：
   - 位置偏差（A/B 順序影響分數）；
   - 長度偏差（偏好較長文本）；
   - 第三種偏差因現場設備故障未講到。
   - 失敗例：退休者要求推薦商品的種子，被改寫成「我每個月需要現金流，推薦哪個產品」，
     丟失「退休」背景，judge 仍給過——應整題剔除。
8. **評估指標**：該擋的有沒有擋（攔截率）、有沒有漏（漏放）；放行題是否被誤擋。
9. **心態**：護欄不是 100% 防護，而是說得出「測了哪些情境、幾筆資料、攔截成功率多少」。
   實務上會疊多種 guardrail（主題、個資、業務領域評分）。

## 套到 text2sql（使用者選擇 B，2026-11-07）

B = 加入不該查資料的題目，攔截與放行各半。

| 演講步驟 | text2sql |
|---|---|
| 政策 | 放行：能用 `sales_data` 回答的唯讀銷售查詢。攔截／不查資料：寫入或修改請求、資料庫外問題、閒聊等（類別待定） |
| 種子 | 放行側由舊模板產生（`scripts/build_golden_seeds.py`，SQL 與 pandas 雙重計算一致才收）；攔截側手寫 |
| 保留欄位 | 放行題：地區、國家、指標、時間、分組、Top-N；攔截題：所屬類別與意圖 |
| 生成 | 本機 Qwen 分階段改寫 |
| 規則層 | JSON、長度、繁體中文，程式判斷 |
| 標籤層 | 放行題標準答案由 SQLite 重新計算；攔截題確認仍屬原類別 |
| 語意層 | judge 檢查是否偏離原意，並人工抽查 |
| 指標 | 攔截題被擋比例、放行題被誤擋比例、放行題答對率；分別測兩條路線 |

## 種子的可信度從哪裡來

改寫與檢查只能保證「改寫沒偏離種子」，種子本身必須另外可信：

- 黃金種子不由 LLM 撰寫：題目來自舊模板，答案由 SQL 與舊 pandas 程式兩條獨立路徑計算，必須一致。
- 別名不再複製成多筆種子，而是當作實體的可用寫法；每個題型只取少量實體，並輪流涵蓋不同地區、類別。
- 題意與答案不一致的模板（I 題）直接排除，原因寫在建置輸出。
- 攔截種子數量少、只有擋／放行，由人工確認標籤。
