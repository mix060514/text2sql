你要替我向技術面試官介紹一個我做的專案。下面是專案的全部事實，請只根據這些事實寫，不要補充我沒提供的數字、
功能或結論；不確定的地方就不寫。

## 專案是什麼

Text-to-SQL 問答系統：使用者用中文問銷售資料（例如「EMEA 的總銷售額是多少？」），系統寫 SQL、唯讀查詢、
檢查答案是否對題，然後回傳說明文字、完整資料表與圖表。

- 模型：全部跑在本機單張 GPU 上的 27B 開源模型（Swift 1.5，Qwen3.8-27B 的後訓練版，IQ3_XXS 量化，
  llama.cpp 伺服器，同時處理 4 個請求）。不呼叫任何雲端模型。
- 資料庫：SQLite 單表 `sales_data`，3 萬筆訂單，2023–2024 年，4 個地區、13 個國家、3 個產品類別、11 項產品。
- 技術：Python、Google ADK、LiteLLM、Pydantic、SQLite、Plotly、Streamlit。

## 核心設計：模型負責想，程式負責做

小模型不可靠的地方不靠提示詞要求它「務必」做到，而是把流程交給程式控制。固定流程如下，
四個模型步驟都不帶工具，模型無法跳過或忘記任何一步：

1. 判斷意圖（模型，不思考）：要求改資料、資料庫沒有的資料、閒聊、提示注入，由程式用固定文字拒答，
   不寫也不執行 SQL；模型給的理由只進紀錄，不回顯給使用者。
2. 寫 SQL（模型）：產生一條 SELECT。
3. 執行 SQL（程式）：唯讀連線加上 SQLite authorizer，只允許單一 SELECT、只能讀這張表；
   5 秒、200 列、20 KB 上限，超過就算失敗，不接受被截斷的結果。
4. 審查是否對題（模型）：拿原問題、業務定義、實際 SQL 與查到的資料，檢查指標、篩選、時間、分組、排序。
   「能執行」不等於「答對」，例如問銷售量卻用訂單數算會被退回。
5. 寫說明與圖表規格（模型）：只寫解釋文字與「畫哪種圖、用哪些欄位」。
6. 發布（程式）：確認審查接受的就是這一次的 SQL 與資料，檢查圖表欄位真的存在且是數值，
   由程式從實際查詢結果產生資料表並用 Plotly 畫圖。答案裡的數字與圖表都不是模型寫出來的。

其他規則：

- 有限重試：只有明確的驗證或執行錯誤才重試，寫 SQL（含審查退回）最多 3 次，寫說明最多 2 次；
  連線或逾時錯誤直接停止。每題最多 9 次模型呼叫、600 秒。
- 狀態隔離：每一回合開始先清掉上一題的查詢結果與圖表，追問只帶上一題成功的問題與 SQL，
  舊結果不會被當成新證據。
- 可追溯：每一步的輸入、輸出、耗時都記錄下來，網頁的對話頁會畫成可點擊的流程圖，
  可以查到答案的每個數字來自哪一次查詢。

## 怎麼驗證它答得對

用一張考卷，84 題，每題考不同的東西、只問一次，分五組：基本查詢 14、畫圖 10、多步驟查詢 30
（子查詢、視窗函數、跨年比較）、不同叫法 10（問題裡的地區或國家名稱和資料庫存的不一樣）、該拒答 20。

- 標準答案不由人或模型填寫：每題事先附一條 SQL，拿到資料庫執行的結果就是標準答案。
- 批改全由程式做，不用 LLM 當評審：該回答的題目，系統實際查出的資料列要和標準答案逐列相符，
  要畫圖的題目再比對圖表類型、橫軸順序、序列數；該拒答的題目，整輪不能有任何 SELECT 成功執行。
- 為什麼不用 LLM 評審、也不把同一題換句話多問幾次：早期版本兩種都做過。LLM 評審會改錯；
  換說法造成的結果差異（8–9/68）和同一句話重跑的差異（13/102）分不開，量不到想量的東西。

## 成績（2026-11-10，整份實跑，不沿用舊結果）

- 總分 82/84。該回答的題 62/64（96.9%），該拒答 20/20，誤擋（該回答卻拒答）0/64，執行錯誤 0。
- 依難度：簡單 17/17、中等 12/12、困難 5/5、多步驟查詢 28/30。
- 平均每題 90 秒（4 題同時跑），最慢一題約 500 秒。
- 錯的 2 題：
  - 「2024 年有幾位客戶三種產品都買過？」：審查步驟認為「三種產品」應該用產品名稱而不是產品類別來算，
    連續退回 3 次，最後沒有發布答案。系統選擇不回答，而不是回答一個沒通過審查的數字。
  - 「日本在該區域的營收名次是第幾？」：系統答第 1 名，標準答案是第 5 名。SQL 先用 WHERE 篩到只剩日本一列
    才算 RANK()，所以永遠是第 1 名；這是真的答錯，而且審查步驟沒有抓到。
- 同一張考卷當天整份跑了四次，成績是 81、81、83、82（該拒答每次都是 20/20，誤擋每次都是 0）。
  這次錯的 2 題在前三次都通過；每次錯的題目不完全相同，單次成績有一到兩題的浮動，來自模型每次作答的隨機性。
  四次之間有修正：換掉 2 題有歧義的問法、圓餅圖改由程式固定由大到小排列、提示詞加一條季度標籤規則。
- 離線測試（真實 SQLite、假模型注入各種錯誤，不呼叫模型）全數通過。
- 加入意圖判斷之前，該拒答的題目只擋下 7.9%（10/126），加入後 99.2%（125/126）。

## 已知限制（請照實寫，不要淡化）

- 審查步驟和寫 SQL 是同一個模型，可能有共同盲點；審查接受不代表數學上的保證，所以另外保留考卷批改。
- 單張 GPU、27B 模型，平均一題約 90 秒，不適合需要即時回應的場景。
- 該拒答的 20 題由 AI 起草與複查，尚未經人工確認。
- 對話狀態存在記憶體，服務重啟後不保留。
- 只有一張表、一個資料庫；沒有測過多表 JOIN 的情境。

## 請你產出

用繁體中文寫一份 3 分鐘內讀得完的專案介紹，讀者是技術面試官。順序：

1. 一句話說明這個專案做什麼。
2. 我要解決的問題：小模型做 Text-to-SQL 時，哪些地方不可靠。
3. 我的做法：哪些事交給模型、哪些事由程式保證，各舉一個具體例子。
4. 怎麼證明有效：考卷的做法與成績，包含錯的 2 題各是什麼情況。
5. 已知限制。

寫法要求：陳述事實與數字，不用形容詞誇獎；每個數字都要能在上面的資料找到；不要寫給我的建議或後續規劃。
